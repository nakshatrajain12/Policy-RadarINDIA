# Policy Radar India — 25 Essential Viva Q&A Defense Guide

This document prepares you for technical and design cross-examination by university professors, department heads, and external examiners during your B.Tech Project (BTP) viva.

---

### Q1: What is the primary novelty of Policy Radar India compared to the official Startup India portal?
**Answer:** The official Startup India portal is primarily a static repository where founders must read dense PDF guidelines and deduce eligibility themselves. Policy Radar India introduces three engineering breakthroughs:
1. **Tri-State Rule Evaluation (`met | not_met | unknown`)**: Evaluates precise eligibility constraints (stage, sector, location, entity type, DPIIT status) rather than keyword guessing.
2. **The Unlock Simulator**: Instead of merely showing current eligibility, it simulates how strategic actions (such as acquiring DPIIT recognition or incorporating as a Pvt Ltd) unlock latent schemes and quantifies the exact monetary value of doing so.
3. **Macro Opportunity Heatmap**: Visualizes capital saturation vs. white spaces across 8 industry verticals and 4 maturity stages for policymakers.

---

### Q2: Explain your Medallion Data Pipeline Architecture.
**Answer:** We implement an automated Medallion data engineering pattern:
- **Bronze Layer (`schemes_raw`)**: Raw, immutable HTML and JSON responses ingested from web scrapers, Open Data portals, and gazettes with extraction timestamps and content SHA-256 hashes.
- **Silver Layer (`schemes_clean`)**: Validated via Pydantic schemas, deduplicated using RapidFuzz string similarity, cleansed of HTML artifacts, and mapped into canonical taxonomies.
- **Gold Layer (`analytics_snapshots` & Materialized Views)**: Pre-aggregated metrics (funding by ministry, sector distributions, stage coverage, state density) cached for sub-100ms API delivery.

---

### Q3: How do you normalize noisy, unstructured government text into controlled taxonomies?
**Answer:** Government portals refer to identical concepts using varied terms (e.g., *"Proof of Concept"*, *"TRL 4"*, *"Early Stage"*, *"MVP"*). In `pipeline/taxonomy.py`, we maintain canonical dictionaries and bidirectional normalization functions:
- **4 Canonical Stages**: `Idea`, `Prototype/MVP`, `Early Revenue`, `Growth/Scale-up`.
- **25 Canonical Sectors**: With over 150 synonym mappings (e.g., "artificial intelligence", "deep learning", "neural networks" → `AI / Machine Learning`).
- **36 Indian States and UTs**: Standardized against ISO 3166-2:IN codes with "Pan-India" fallback.

### Q4: What mathematical formula governs your scheme recommendation scoring?
**Answer:** We compute a composite relevance score bounded between $[5, 99]$:
$$\text{Score} = w_{\text{rule}} \cdot S_{\text{rule}} + w_{\text{geo}} \cdot S_{\text{geo}} + w_{\text{sector}} \cdot S_{\text{sector}} + w_{\text{bonus}} \cdot S_{\text{bonus}}$$
Where:
- $S_{\text{rule}} \in [0, 100]$: Weighted score from the tri-state evaluator across DPIIT, Entity Type, Stage, and Age constraints.
- $S_{\text{geo}}$: $+10$ boost for localized state matching; $-35$ penalty if restricted to an unmatching state.
- $S_{\text{sector}}$: $+8$ boost for direct sector alignment.
- $S_{\text{bonus}}$: $+15$ bonus for women-led enterprises matching targeted women entrepreneurship funds; $+5$ bonus for non-dilutive grant instruments.

### Q5: How does your system evaluate eligibility when founder information is missing?
**Answer:** Traditional binary filters (`True/False`) fail on partial data, either improperly rejecting founders or giving false positives. We utilize a **Tri-State Logic Engine**:
- `met`: Startup definitively satisfies the guideline.
- `not_met`: Startup definitively violates a mandatory constraint (hard exclusion).
- `unknown`: Missing information (e.g., founder hasn't specified DPIIT status). The scheme is neither excluded nor fully credited; it is flagged with a prompt to confirm the attribute.

---

### Q6: How do you guarantee zero LLM hallucination in scheme names and funding numbers?
**Answer:** We enforce a strict **Factual Bounding Constraint**:
1. All scheme data (names, funding caps, portal URLs) are stored in structured PostgreSQL tables, not generated by an LLM.
2. The AI Executive Brief is generated from a rigid facts dictionary computed by `pipeline/analytics_engine.py`.
3. The Fast-Path Copilot router extracts numbers and counts directly using deterministic SQL/Python aggregations, completely bypassing LLM text generation for quantitative answers.

---

### Q7: Why is your Copilot latency sub-millisecond (0.04 ms) instead of 3–5 seconds like typical LLM chatbots?
**Answer:** Most AI dashboards route every question through an external LLM API (e.g., OpenAI or Gemini), incurring prompt token serialization, network transit, and autoregressive generation latency. 
Our `CopilotEngine` utilizes a **Deterministic Intent Router**: queries matching common operational patterns (*"How many schemes?", "Schemes in Karnataka", "Top grants", "DPIIT requirements"*) are parsed and answered directly from in-memory indexed Python structures in **0.02 to 0.04 milliseconds**. Only ambiguous, open-ended strategic questions fall back to the LLM.

### Q8: What are Precision@5 and nDCG@5, and what were your empirical results?
**Answer:**
- **Precision@5**: The fraction of the top-5 recommended schemes that are genuinely relevant and actionable for the startup's profile. We achieved **82.0%** (target: >80%).
- **nDCG@5 (Normalized Discounted Cumulative Gain)**: Evaluates whether the most relevant schemes appear at the top of the list rather than lower ranks, penalizing misranked items logarithmically:
  $$\text{DCG}@K = \sum_{i=1}^K \frac{2^{\text{rel}_i} - 1}{\log_2(i + 1)}, \quad \text{nDCG}@K = \frac{\text{DCG}@K}{\text{IDCG}@K}$$
  Our system achieved an nDCG@5 of **0.957** (target: >0.85).
- **Ineligible Scheme in Top-5 Rate**: **0.0%** (target: <5.0%).

### Q9: How do you handle cold-start problems for newly registered users?
**Answer:** If a user logs in for the first time without custom input, the system loads a sensible baseline profile (`AgriTech • Idea Stage • Karnataka • Non-DPIIT`) and automatically presents the **Founder Profile & Intake Modal**. In 3 clicks, the founder chooses their domain, stage, and state, which instantly re-scores and re-renders the dashboard without requiring a page reload.

### Q10: How did you implement deduplication across diverse scraper sources?
**Answer:** In `pipeline/excel_importer.py` and `pipeline/bronze_runner.py`:
1. **Canonical Name Normalization**: Lowercasing, stripping punctuation, expanding acronyms (e.g., "SISFS" ↔ "Startup India Seed Fund Scheme").
2. **Fuzzy String Distance**: RapidFuzz token sort ratio. If similarity exceeds $88\%$, the pipeline merges fields rather than creating a duplicate row, preserving the latest scraped timestamp and the most descriptive gazette summary.

---

### Q11: How do you respect ethical and legal web scraping standards?
**Answer:**
1. We strictly parse and respect `robots.txt` for all accessed domains.
2. We rate-limit requests to $\le 1$ request/second per host with exponential backoff on HTTP 429/5xx responses.
3. We store only factual public government information and short evidentiary quotes with explicit source attribution and official portal links; we do not scrape paywalled or authenticated personal data.

---

### Q12: Explain your database schema and indexing strategy.
**Answer:** In Supabase PostgreSQL (`schemes_clean`):
- B-Tree indexes on scalar lookup columns: `level`, `geographic_restriction`, `status`, `review_status`.
- GIN (Generalized Inverted Index) indexes on PostgreSQL array fields: `sector_eligibility`, `startup_stage`, and `tags` to support fast array containment queries (`@>`).
- Composite unique index on `(sector, stage, state)` in `recommendation_cache` for instant repeat profile queries.

### Q14: How does the Unlock Simulator compute its insights?
**Answer:** For every scheme in the database, the engine runs an eligibility check. If a scheme is rejected **solely** due to a single addressable prerequisite (e.g., lacking DPIIT recognition or corporate registration as a Pvt Ltd), it is classified as an *Unlockable Opportunity*. The engine sums the capital caps of all unlockable opportunities to display: *"Acquire DPIIT to unlock 14 schemes worth ₹1.85 Cr"*.

---

### Q15: What happens if an external government portal URL breaks or undergoes restructuring?
**Answer:** The daily automated verification pipeline (`daily_pipeline.yml`) executes periodic HTTP HEAD/GET health checks on all stored `source_url` and `application_portal` links. Any endpoint returning non-200 status codes flags a review alert in `scheme_sources` while falling back to the parent Ministry or Startup India portal.

### Q16: How is user authentication handled?
**Answer:** We leverage Supabase SSR Auth with secure HTTP-only cookies in Next.js middleware. To facilitate viva demonstrations where examiners do not have personal accounts, we also support an instant demo profile mode with seamless localStorage persistence.

### Q17: What is the benefit of the unified `/analytics/bundle` endpoint?
**Answer:** The previous architecture made 5 distinct, uncoordinated HTTP requests (`/summary`, `/funding-by-ministry`, `/sector-distribution`, `/stage-coverage`, `/detailed`) on page load. `/analytics/bundle` aggregates summary KPIs, ministry bars, sector distribution, stage breakdown, state density, heatmap matrix, and the verified AI brief into a single payload, served from an in-memory cache in **0.007 milliseconds**.

### Q18: What Machine Learning or NLP models are employed in the pipeline?
**Answer:**
1. **Sentence Transformers / Gemini**: Extracts structured eligibility attributes from raw PDF gazettes into normalized JSON.
2. **RapidFuzz Levenshtein Distance**: Fuzzy deduplication of scheme names across scrapers.
3. **Discounted Cumulative Gain Ranking**: Validates the ordering quality of recommendations.

### Q19: How are women founders and marginalized entrepreneurs prioritized?
**Answer:** Schemes targeting women-led startups (e.g., *ELEVATE WomEN Karnataka*, *WE-Hub Telangana*, *WISE-KIRAN DST*) receive positive heuristic boosts when `women_led: true` is set. Similarly, state policies offering enhanced subsidies (e.g., Bihar Startup Policy's extra 5% grant or Karnataka Unnati SC/ST) are highlighted with affirmative criteria flags.

### Q20: What security measures prevent prompt injection or SQL injection?
**Answer:**
1. **Parameter Binding / PostgREST ORM**: All database interactions use parameterized queries via the Supabase client, preventing SQL injection.
2. **Scraped Content Sanitization**: Scraped text is stripped of HTML scripts, capped in length, and parsed with strict Pydantic schemas before storage.
3. **LLM Context Isolation**: Prompts ground the LLM in structured facts rather than raw untrusted web HTML.

### Q21: What are the key limitations of your current system?
**Answer:**
1. Application forms on certain state portals require regional language OCR (e.g., Kannada, Odia) which requires ongoing translation refinement.
2. Some state schemes have fluctuating annual budget outlays that depend on state legislative appropriations.

### Q22: How does the system ensure fast client-side performance?
**Answer:**
- Static site generation (SSG) for static routes via Next.js 16.
- In-memory data caching on the FastAPI backend with 5-minute TTL.
- Zero render-blocking external font CSS imports (dropped external CDN font links in favor of native SVG Lucide icons).
- Debounced client-side filtering for 193 schemes with instant UI updates.

### Q23: Could this platform scale to monitor global startup policies (e.g., USA, UK, Singapore)?
**Answer:** Yes. The taxonomy schema in `pipeline/taxonomy.py` is modular: swapping the state code dictionary for ISO 3166-1 alpha-2 country codes and adding currency conversion modules allows the same tri-state engine and unlock simulator to support global innovation programs.

### Q24: What were the most challenging engineering bugs you solved during the project?
**Answer:**
1. **Turbopack SSR Font Resolution**: Next.js 16 Turbopack build failure due to multiple weight arrays on variable Google Fonts; resolved by adopting variable font definitions.
2. **Tri-State Gating Disqualification**: Resolving an issue where unregistered idea-stage founders were inadvertently hard-excluded by Pvt Ltd constraints; solved by adding `unregistered_idea` to canonical entity types.
3. **Supabase Stale Connection Pools**: Fixed by implementing auto-reconnecting `safe_query` wrappers with HTTP/2 client recreation.
